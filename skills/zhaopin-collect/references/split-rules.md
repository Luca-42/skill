# 分片边界、去重、串库防护

## 1. 分片职责边界

边界靠"单位归属"划，不靠"公告来源"。一个单位只归一个分片，否则会重复计数。

| 分片 | 收 | 不收 |
| --- | --- | --- |
| 考公 | 国考、各省省考、定向选调、选调生 | 事业单位、教师、国企 |
| 考编 | 事业单位统考、教师编、医疗卫生编、三支一扶、**雄安新区** | 公务员（含选调）、央国企校招 |
| 能源军工 | 电网、发电、油气、煤炭、烟草、核工业、航天航空兵器船舶电科 | 建筑、交通、通信、金融、银行 |
| 建筑通信金融 | 建筑基建、通信运营商/铁塔、铁路/邮政/航运/招商局/华润/中粮/宝武/五矿、六大行+政策性银行 | 能源、军工 |

**国铁集团归建筑通信金融**（不是交通另开一片）；**烟草归能源军工**。

## 2. 同日同项目合并（build_list 内）

两个分片同时收到同一单位时，`build_list.py` 会按**项目名互为子串**合并：

- `2027届秋季校园招聘` ⊂ `2027届秋季校园招聘（总部河北雄安…）` → 合并，保留更长的项目名，互补 `岗位表文件` / `官网` / 备注
- `2027年高校毕业生招聘（第一批）` 与 `（提前批：…）` **互不包含** → 保留两行（是不同批次，正确）

所以：**项目名不要为了"好看"改短**，改短会导致漏合并或误合并。

## 3. 跨轮去重

`build_list.py` 会丢弃"上一轮遗留、且本轮同单位已有新条目"的旧行。
单位名比对时忽略末尾括号，例如 `中共成都市委组织部` 与 `中共成都市委组织部（成都市）` 视为同一单位。

因此采集时**不要给单位名加/减括号后缀**——那是重复行的主要来源。

## 4. 串库防护（重要）

工作区可能同时存在多个清单（考公考编央国企 / 外企 / 雄安），各有独立分片与台账。

`build_list.py` 顶部有显式白名单：

```python
SHARDS = ("raw_考公.json", "raw_考编.json", "raw_能源军工.json",
          "raw_建筑通信金融.json", "raw_手工补录.json")
```

**不要改回 `raw_*.json` 通配。** 曾因此差点把 148 条外企岗位混进主清单（总数会从 187 跳到 335）。
同理 `sync_raw.py` 也用了白名单——它原先用通配，读到结构不同的 `raw_雄安_jobs.json`（是 list 不是 dict）直接崩了。

新增分片时：**同时**加进 `build_list.py` 的 `SHARDS` 和 `sync_raw.py` 的 `SHARDS`。

各库的隔离红线：

| 库 | 分片 | 台账 | 目录 | 快照 |
| --- | --- | --- | --- | --- |
| 考公考编央国企 | `raw_考公/考编/能源军工/建筑通信金融/手工补录` | `units.json` | `岗位列表/{考公,考编,央国企}` | `数据/历史/` |
| 外企 | `raw_外企.json` | `units_外企.json` | `岗位列表/外企/` | `数据/历史_外企/` |
| 雄安 | `raw_雄安_*.json` | 独立 | `岗位列表/雄安/` | 独立 |

## 5. 手工补录

`数据/raw_手工补录.json` 只放"常规四路覆盖不到、人工确认过"的单位。
它不参与 subagent 覆盖写，所以不会被明天的采集冲掉；`build_list.py` 照常合并。

每轮开跑前扫一眼，确认里面的状态/日期还有效。过期条目会按日期规则自动翻 `已结束`，不用手删。

## 6. 一个分片由谁写

- 分片 agent **只写自己那一个** `raw_<块>.json`
- **绝不**写 `units.json`、清单 `md`、`raw_手工补录.json`、别的分片
- 分片 agent 挂了 → 主流程按"只补缺口"原则重跑，不要让它顺手把别人的分片也覆盖了
