# 状态判定规则

`build_list.py` 的 `auto_status()` 实现，下面是从实际踩坑里定下来的口径。

## 判定顺序

按顺序命中即返回，前者优先：

| 序 | 条件 | 结果 | 备注文案 |
| --- | --- | --- | --- |
| 1 | `状态` 已是 `已结束`，且截止日不晚于今天 | `已结束` | 保留原备注 |
| 2 | 解析出的截止**时刻**已过 | `已结束` | `报名已于 MM-DD HH:MM 截止` |
| 3 | 今天 < 报名开始 | `未开始` | `报名 MM-DD 开始` |
| 4 | 报名开始 ≤ 今天 ≤ 报名截止 | `招聘中` | `报名至 MM-DD（剩 N 天）` |
| 5 | 只有截止日且今天 ≤ 截止 | `招聘中` | 同上 |
| 6 | 其它 | 沿用采集值；缺失则 `待确认` | |

## 时刻（HH:MM）的处理

- `报名截止` 里带 `HH:MM`（如 `2026-11-04 08:00`）→ 按 datetime 比较，**过了时刻当场翻已结束**
- 只有日期（如 `2026-11-04`）→ 视为当天 **23:59** 截止

这条是为**晚间运行**加的：日程从 10:00 改到 20:00 后，`10-31 18:00` 截止的单位在 20:00 会显示"还能报"，是错的。

同理，`10-29 08:00` 截止的四川 7 个批次，如果字段只写 `2026-11-04`，会在当天 20:00 仍显示"招聘中"。**采集时能拿到时刻就要写进字段。**

## 规则 1：已结束不复活

采集员已判 `已结束`、且截止日不晚于今天时，**不再按日期翻回 `招聘中`**。

来源：某单位公告只写"报名至 11 月 3 日"，实际 16:00 就关网了。采集员按当天截止判了 `已结束`，但 `build_list` 只比日期，又把它翻回"招聘中"，用户看到错误的可报状态。

## 口径要写进备注

以下几种"截止日"不是官方明文，必须注明来源，不能当成硬承诺：

| 口径 | 来源 | 备注写法 |
| --- | --- | --- |
| 才立方"过期时间" | 高校就业网页面展示期 | `截止取才立方过期时间，非单位明文` |
| 集团最早的子企业截止 | 子企业各自挂网 | `按子企业最早口径（XX 11-07；YY 12-31）` |
| 只有"即日起—X月X日" | 公告正文 | 直接记日期，备注引原文 |
| 完全没写截止 | 滚动招聘 | `报名截止` 留空，状态靠采集值（多为 `招聘中`） |

## 状态值只有四个

`招聘中` / `已结束` / `未开始` / `待确认`。

不要自创"即将截止""滚动招聘"之类——排序和统计都按这四个值走。
"滚动招聘"是备注里的描述，不是状态。

## 排序

| 状态 | 排序 |
| --- | --- |
| 招聘中 | 截止日**升序**（最急在前），无截止日的排最后 |
| 未开始 | 同上 |
| 待确认 | 按单位名 |
| 已结束 | 截止日**降序**（最近结束的在前） |

## 统计口径

清单头部四个数字必须满足：

```
在招 + 未开始 + 已结束 + 待确认 = 总单位数
```

`verify.py` 会核这个。对不上说明有手改或合并异常。
